## 一、项目一句话介绍（先把这个背熟）

> 一个基于大模型的旅行行程推荐系统：用户输入一句话旅游需求（比如「北京出发、5 天、5000 预算、带父母」），系统用 LLM 解析意图 → 从 20 条现成路线和 80 个景点中召回候选 → LLM 重排生成个性化行程 → SSE 流式返回；同时提供路线预订、行程规划、大屏运营看板、AI 情感分析等能力。

**技术栈**：Spring Boot 4.0.8 + Java 17（编译目标）+ MyBatis-Plus 3.5.16 + Spring Security 7 + JWT + Vue 3 + Vite 8 + Redis + MySQL 8.0 + Spring AI 2.0（AI 业务待接入）+ Knife4j

**五层架构**（01 文档）：前端展示层 → API 网关层（JWT+限流）→ 业务服务层 → LLM 工程化层（意图解析/混合推荐/RAG）→ 数据层（MySQL+Redis+向量库）

### 3.2 建表关键裁定（B1~B9，答辩「为什么这么设计」的现成答案）

| 编号 | 裁定 | 理由 |
|---|---|---|
| B1 | `route.recommend_weight decimal(5,4)` 存 0~1，默认 0.5 | 权重要进混合推荐公式参与乘法，0~1 语义清晰 |
| B2 | 第 27 张表 `route_comment_like`，`uk(user_id, comment_id)` | 评论点赞幂等，唯一键天然去重 |
| B3 | `route_comment.sentiment_retry tinyint unsigned default 0` | 情感分析失败重试次数留痕，AI 稳定性可观测 |
| B4 | `route.quota_per_day int unsigned default 20` | 预约人数上限字段，BR-INT-04 名额校验需要 |
| B5 | `user_plan.destination_ids varchar(255)` 逗号分隔 | 规划多目的地，简单够用 |
| B6 | `stat_daily` 长表 `uk(stat_date, metric_key)` | 大屏/AI 洞察数据源，预聚合宽表 |
| B7 | `prompt_template.code + uk(code, version)`，同码仅一条启用 | 提示词版本管理，回滚有依据 |
| B8 | `route_booking` 索引 `(user_id, route_id, travel_date)` + Service 层查重 | 业务规则前置校验，不用脆弱的组合唯一 |
| B9 | `destination.route_count` 冗余数字段 | 列表页免 join，读多写少场景划算 |

### 3.3 建表约定

`utf8mb4` / InnoDB / `bigint unsigned AUTO_INCREMENT` 主键 / 业务侧维护计数字段 / 8 张逻辑删除表（`deleted=1`）/ 时间统一 `datetime` / 字符串 `NOT NULL DEFAULT ''` 除非可空。

## 六、关键决策与踩坑记录（复盘重点，也是答辩素材）

> 「老师，这个坑我是真的踩过，下面是我当时怎么修的」——答辩现场最有说服力的内容。

### 6.1 数据库脚本阶段（第 0 步）

| 坑 | 现象 | 修复 |
|---|---|---|
| 网上流传的 BCrypt 哈希 | `$2a$10$7JB720yubVSZvUI0rEqK/...` 实测对应明文是 **admin123** 不是 123456 | 用 Python bcrypt 实测生成并验证 `123456` 的哈希 |
| `sys_user.email` 重复空串 | `data.sql` 导入报 `Duplicate entry '' for key 'uk_email'`（20 个用户都是 `''`） | 空邮箱改存 **NULL**——MySQL 唯一索引允许多个 NULL，但不允许重复空串 |
| banner 时间列错位 | `Incorrect datetime value: '1' for column 'start_time'` | 生成器取错元组下标 `b[6]`→`b[7]`（start_time） |
| INSERT 缺分号/逗号 | 语句连成一片 | 生成器加收尾校验 post-pass |
| 演示数据天数对不上 | 文档写 79 天/276 项，初稿 82/285 | 把 208/210/220 三条路线从 5 天改 4 天，与文档完全对齐 |

### 6.2 后端阶段（第 1 批）

| 坑 | 现象 | 修复 / 决策 |
|---|---|---|
| `id-type: assign_id` 与 schema 不符 | 文档模板默认雪花 ID，但我们的 schema 是 AUTO_INCREMENT | 配置改 **`auto`**，用 `SHOW CREATE TABLE sys_user` 现场核实 |
| 登录被校验拦截 | `LoginDTO.password @Size(min=8)` 把 6 位 `123456` 挡在门外 | **登录不校验密码策略**（那是注册侧的 BR-USR-02），删最小长度 |
| `@MapperScan("com.trip.module.**.mapper")` | 通配符 basePackage 会**静默注册 0 个 Mapper**，启动即败 | 改为显式列出 3 个 mapper 包 |
| 文档写 `RoutePlace` | 实际表是 `route_item` | 实体命名以 schema 为准：**RouteItem** |
| Jackson 3 包名 | Boot 4 用 Jackson 3（`tools.jackson.databind`） | 注解仍是 `com.fasterxml.jackson.annotation.*`（已在 .m2 仓库核对 jar），实体时间格式用 `@JsonFormat(pattern="yyyy-MM-dd HH:mm:ss", timezone="GMT+8")` |
| Spring Security 7 语法 | 网上 90% 教程是 Boot 3/Security 6 | `.and()` 已删；`authorizeHttpRequests/requestMatchers`；`dispatcherTypeMatchers(ERROR,FORWARD).permitAll()` 防异常被拦成 401；路径匹配 `**` 只能放末尾 |
| JWT 过滤器异常没人接 | `@RestControllerAdvice` 管不到 DispatcherServlet 之前的过滤器 | 过滤器内自己 catch 并直接写 401 JSON |
| authority 前缀 | `hasRole("ADMIN")` 会自动补 `ROLE_` 比对 | authority 必须存 `ROLE_ + role` |
| 委派密码编码器 | `PasswordEncoderFactories` 对裸 `$2a$` 哈希抛 `no PasswordEncoder mapped` | 只用 `new BCryptPasswordEncoder()` |
| JJWT 0.12 API | 0.11 的 `parseClaimsJws().getBody()` 已删 | `Jwts.parser().verifyWith(key).build().parseSignedClaims(token).getPayload()` |
| JPMS 模块化构造器注入 | — | `JwtUtil` 用 `@Value` 构造注入（secret ≥32 字节防 WeakKeyException） |

### 6.3 Boot 3 → Boot 4 断代差异（照抄旧教程必炸，答辩可以直接背）

| 项 | Boot 3 / Security 6 | Boot 4 / Security 7 |
|---|---|---|
| Web 起步依赖 | `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| Security 链式 | `.and()` 链 | `.and()` 删除，单独 lambda |
| 授权方法 | `authorizeRequests()/antMatchers()` | `authorizeHttpRequests()/requestMatchers()` |
| 路径匹配 | AntPath/MvcRequestMatcher | `PathPatternRequestMatcher`，`**` 仅限模式末尾 |
| Jackson 核 | `com.fasterxml.jackson.databind.ObjectMapper` | `tools.jackson.databind.ObjectMapper` |
| MyBatis-Plus | boot3-starter | `mybatis-plus-spring-boot4-starter`，分页器需补 `mybatis-plus-jsqlparser` |
| 测试依赖 | 单个 `spring-boot-starter-test` | 按模块拆分（webmvc/validation/security/redis/actuator 各自 test） |

## 八、答辩高频追问 Q&A（现在就能答的）

**Q1：为什么 27 张表？数据怎么分组？**
六组：用户组（sys_user / user_preference / user_behavior）、内容组（destination / attraction / route / route_day / route_item）、互动组（like / favorite / booking / comment / comment_like）、规划组（user_plan 三表）、AI 组（会话/消息/调用日志/洞察/知识库）、运营组（banner / feedback / 配置 / 提示词 / 统计 / 操作日志）。第 27 张是评审补的评论点赞表（B2 裁定）。

**Q2：为什么用冗余计数字段（like_count、view_count…而不是实时 count）？**
读多写少场景：详情页一次展示 6 个计数，实时聚合要 6 次 join/子查询；冗余字段一次查回。代价是写操作要事务内双写，用唯一键 + Service 层保证一致性。

**Q3：自增主键还是雪花？**
演示规模用自增（`bigint unsigned AUTO_INCREMENT`），ID 可读、索引紧凑、与演示数据一致；规模大了再换雪花或分布式 ID 也不影响业务代码（MyBatis-Plus 的 id-type 一处配置）。

**Q4：密码安全怎么做的？**
BCrypt（自适应哈希、自带盐、慢哈希抗彩虹表）。演示坑：网上流传的哈希对应明文是 admin123 而不是 123456，我实测校验后替换。

**Q5：JWT 为什么无状态？怎么退出登录？**
JWT 自包含用户身份，服务端不存会话，天然水平扩展；退出/封禁把 token 加入 Redis 黑名单（accessToken 2 小时 / refreshToken 7 天，BR-USR-04）。

**Q6：AI 推荐为什么会胡说？怎么兜底？**
结构化输出 + JSON Schema 约束（09 文档）→ 意图解析失败给 3002 并降级基础推荐（热度 + 运营权重 recall/rank）；RAG 引用溯源，知识库无内容给 3003；LLM 调用熔断降级有 llm_call_log 全程留痕（3001）。

**Q7：SSE 流式为什么可行？**
`server.tomcat.max-swallow-size=-1` + text/event-stream，前端骨架屏 + 首包超时降级（06 风险表）。

**Q8：项目的 7 个创新点是什么？**
按 `docs/01` 第六章背（LLM 意图解析、混合推荐+重排、RAG 问答引用溯源、AI 行程生成、评论情感分析、AI 数据洞察、运营干预权重）——第 3 批做完后每个创新点配一个可演示功能。
