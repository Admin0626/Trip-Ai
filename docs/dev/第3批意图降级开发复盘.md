# 第3批意图降级开发复盘

## 本次解决的问题

原来AI接口只有设计文档，本阶段交付了可登录调用、可持久化审计、可复现验证的意图解析降级接口。用户明确要求不接真实模型，因此结果诚实标记RULE_FALLBACK，不能在答辩时宣称已完成LLM意图识别或整个第3批。

## 一次请求如何流转

1. 前端或接口工具向`POST /api/ai/recommend/intent`提交query，Authorization携带Bearer JWT。
2. 现有SecurityConfig与JWT过滤器验证身份，控制器从认证主体获得userId，不接受客户端指定用户ID。
3. IntentController保留query原始JSON类型，拒绝数字/对象/null以及不满足长度的字符串。沿用项目协议：业务参数错误HTTP200/code400，鉴权失败HTTP401。
4. IntentService通过参数化JdbcTemplate访问已上架、未删除的目的地，取得名称、省份和城市作为受控词表。无模型客户端初始化或网络模型请求。
5. RuleIntentParser过滤否定子句，提取明确数字和关键词；字段无法确定则null或空数组。0.1/0.3仅是低置信度标记，不是统计校准后的概率。
6. 服务写llm_call_log后返回统一R结构。日志只存userId、INTENT_PARSE、rule-only、耗时、降级标识和MODEL_DISABLED原因，不存完整输入或token。

## 关键设计及取舍

- **为什么DTO中的query是Object？** 单测覆盖的是规则方法，真实HTTP才经过Jackson。实测发现JSON数字会被自动转换成String，因此在接口边界保留类型并主动校验；OpenAPI仍声明字符串，避免误导调用方。
- **为什么unknown不补默认值？** 用户没有说“情侣”就不填couple，区间也不随意取左端。否则召回阶段会用错误条件过滤路线。未知值留给用户确认。
- **为什么使用数据库词表？** 直接复用当前在架目的地，避免写死城市清单与业务数据脱节。代价是当前每次请求读取词表，后续数据量增大再增加缓存和更好的消歧。
- **为什么记录success=0但HTTP成功？** 日志字段描述模型调用是否成功；本阶段完全未调用模型，接口仍成功返回规则结果。is_fallback=1、model=rule-only、MODEL_DISABLED共同明确其含义。后续看板不能把该样本算成供应商故障。
- **为何使用JdbcTemplate？** 当前只有一个词表查询和一条插入，不新增整套实体/mapper。参数化写入userId，错误原因是固定枚举字符串。
- **日志写入失败怎么办？** 当前不吞数据库错误，走全局code500；尚未实现异步审计或数据库不可用时的独立降级。不能宣称任何基础设施故障下都能推荐。
- **输入长度如何处理？** 原始Java UTF-16长度≤500、strip后≥5，超长拒绝而非静默截断。与设计文档“截断并提示”存在明确记录的差异，避免当前响应无法表达截断导致调用方误以为完整理解。

## 答辩时可以怎样解释

“我先把AI能力的失败路径做成独立、可测试的服务。没有模型时，系统仍返回明确的旅行条件，并告诉调用方这是低置信度规则结果。真正连接模型后，会先从数据库加载提示词，校验模型返回的结构，失败重试一次，再复用这条降级路径。此次实测暴露了JSON隐式类型转换和区间误判，因此接口测试覆盖了序列化层，而不只是Java方法。”

## 接下来的开发顺序

用户保持不接模型时，可先做数据库基础召回与推荐页：依据用户确认后的目的地/预算/天数/标签筛选在架路线，返回可解释的基础匹配结果，禁止生成伪造LLM评分。再补用户确认界面、配额与调用统计。

模型阶段仍待完成：专用配置与环境变量、数据库INTENT_PARSE模板渲染、兼容协议客户端、完整输出Schema校验、一次重试、超时/错误降级、可控模型故障测试，最后才是真实模型验收。SSE行程、RAG、规划优化与评论情感分析是后续独立任务。
