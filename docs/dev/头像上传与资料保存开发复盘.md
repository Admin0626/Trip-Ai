# 头像上传与资料保存开发复盘

本轮用户可在“个人资料”选择 PNG/JPEG，看到预览，点击“保存资料”后顶部头像立即同步，刷新页面仍显示保存结果。修复了合法上传路径被拒，以及保存响应返回旧值两个问题。具体数字和响应见[接口实测](头像上传与资料保存接口实测.md)。

## 请求经过哪些模块

1. `Profile.vue` 通过文件输入调用 `uploadImageApi`，FormData 发送到 `POST /api/file/upload`。JWT/Redis会话认证通过后，`FileController` 检查内容、大小、尺寸并随机命名，返回本站地址。
2. 上传只返回文件地址，并没有修改用户资料。前端把地址放进表单显示预览；点击“保存资料”才发送 `PUT /api/user/profile`。
3. 用户ID来自登录身份。`UserSettingsService.updateProfile` 对用户行加锁，合并允许更新的字段，校验后写数据库，返回最新 `UserVO`。昵称、邮箱等走同一路径。
4. 页面将返回值同步到用户状态和本地资料缓存。顶部头像订阅同一状态，因此正确的保存响应直接影响页面是否立即显示新头像。
5. 刷新页面重新读取资料；图片由公开 `/api/files/{name}` 读取。文件名只接受生成器可产生的32位十六进制 `.png/.jpg`，并返回内容类型与 `nosniff`。

## 为什么一个正则会破坏完整流程

接口单独返回200不代表链路成功。上传、资料保存和公开读取必须使用相同的文件名约定。原上传和读取使用去掉短横线的 UUID，资料校验却按带短横线 UUID 长度编写，造成“上传成功，但点击保存报错”。回归必须把上传接口实际返回的地址交给保存接口，不能手写一个刚好满足校验的假路径。

## 为什么数据库更新成功还会返回旧值

本项目同一事务内混用 JdbcTemplate 与 MyBatis。第一次 Mapper 查询会在会话内缓存用户对象；直接 JDBC 更新数据库不经过 Mapper，缓存不知道这次写入。第二次相同 Mapper 查询可能直接返回旧对象，因此“数据库已新、响应仍旧”。

本轮让资料更新经过 Mapper：用 `LambdaUpdateWrapper` 显式设置允许字段，写入后由 Mapper 失效本地缓存，再查询最新资料。没有通过全局关闭缓存、页面强制刷新或延时等待掩盖问题，也没有扩大可修改字段范围。显式设置 NULL 保留清空邮箱/手机号的语义，行锁继续保护两个标签页对不同字段的更新。

## 答辩可以怎样解释验证

- “我们不仅验证code200，还比较保存响应、独立读取与SQL三者的数据。”中间51/53即由新增保存响应断言发现缓存缺陷。
- “上传文件按内容判断类型。”把真实PNG命名为JPG仍生成PNG；伪造PNG扩展名的文本被拒。
- “边界检查和页面检查互相补充。”接口验证体积、像素、非法地址，Edge实际验证预览、保存、顶部头像及刷新保留。
- “失败证据也是结果的一部分。”保留44/51、51/53及最终59/59三个阶段，说明缺陷如何被发现和解决，不覆盖失败报告。

## 仍需接续的边界

本轮保留原上传即存文件的机制，用户上传后不保存资料可能留下未引用文件；生产环境的定期清理、云存储和外部图片域名策略尚未实现。头像图片按现有接口公开读取，不用于私密附件。完整用户认证回归（尤其改密后所有旧会话失效）是下一项工作，不能由本轮头像测试替代。
