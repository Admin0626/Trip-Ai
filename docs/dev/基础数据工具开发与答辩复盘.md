## 导出的实现

AdminUserController提供GET /admin/user/export，UserExportService按相同keyword/status筛选，SQL只选择管理列表字段并排除deleted用户。LIMIT5001用于发现超过5000的请求并明确拒绝，避免静默截断。

使用UTF-8 BOM及CSV标准双引号转义，中文可直接用Excel打开。对首个有效字符为=、+、-、@或开头制表/换行的文本加单引号，避免用户昵称被表格解释为公式。二项单元测试检查公式与逗号/双引号/换行转义，真实接口另检查BOM和公式文本。响应no-store，不包含密码、JWT、邮箱或手机号。前端先判断错误JSON再下载，防止把失败响应保存成CSV。

## 导入的实现

CatalogImportController接受multipart file；CatalogImportService完成严格JSON读取、现有目录DTO/Bean Validation、预览及事务写入。根对象只有version/type/records；version是整数1，一批1至50条且最多1MiB。未知字段、重复键、数字字符串等不宽松接受。

目的地、景点、路线分别复用CatalogService创建流程。景点/路线须指定已有未删除目的地；路线天数匹配dayList，关联景点须属于该目的地且已上架，手工活动attractionId=0。单个标签不能包含逗号。文件内与库中重名均检查，比较规则依照当前MySQL utf8mb4_general_ci。修改数据库排序规则时须同步此比较规则。

预览是只读操作。提交重新校验，任何一行错误都会拒绝整批，任何运行期异常回滚新增目录、每日行程、统计更新及幂等结果。不能把预览结果当作数据库锁定凭证。

浏览器每次预览建立小写UUID，实际提交带requestId和confirmation=确认导入。catalog_import_batch以管理员ID+UUID唯一；存文件SHA-256和结果ID，不存文件原文。同一用户同一编号同一文件回放原结果，不同文件返回409。文件字节不同（即使仅格式空格）视为不同payload。管理员账号行锁串行同用户提交；父目的地按ID排序锁定，与目录维护配合。此设计为本机同步小批处理，不是大规模异步导入平台。

## 注销与并发的实现

POST /user/account/close只从AuthenticationPrincipal取本人ID，请求严格限password和confirmation两个字段。BCrypt校验当前密码，确认文字必须为“注销账号”，拒绝ADMIN账号和待确认/已确认预约。

事务中锁sys_user行；撤销全部Redis会话后设置deleted=1/status=0、随机不可使用密码，昵称替换、头像/电话/邮箱/城市清理，并删除旅行偏好。登录、刷新和创建预约使用同一用户行锁，注销之后的等待请求读到已关闭状态；预约先成功则注销发现未结束预约而返回409。

Redis和MySQL不是分布式原子事务。撤销失败会抛503、数据库注销回滚；若会话已部分撤销但数据库后续回滚，用户可能需要重新登录，旧会话不会因此复活。实际验收覆盖正常Redis、两个设备、预约及刷新并发；没有停机注入Redis失败或生产跨节点测试。

保留用户名占位和业务历史ID，可避免旧评论/预约/规划关联及统计被破坏，也避免旧用户名被新账号接管。历史预约可能仍保留联系方式，旧上传头像文件也未物理删除。此功能是账号关闭与资料清理，不是所有存储中的个人数据彻底擦除；如后续需要完整清除，应新增明确的历史数据处理、共享文件引用与审计策略。已进入其他业务方法的全部并发写请求不在本批逐一验证范围内。

## 答辩问题

| 问题 | 回答要点 |
|---|---|
| 为什么导出不用xlsx？ | 本批需要可用的筛选导出，CSV可被Excel读取且不新增依赖；明确未提供工作簿格式/多Sheet能力 |
| 为什么导入JSON？ | 路线包含每日行程和活动数组，JSON能直接表达嵌套结构并复用已验证DTO；Excel映射属于后续扩展 |
| 出错会不会只导入一半？ | 提交全量重校验及数据库事务；初验café重名在运行期失败，SQL实证整批回滚，后来预览也修正 |
| 用户重复点击会不会新增多份？ | UUID+文件SHA256+用户范围唯一结果，真实并发两请求同一ID，一个首次成功一个回放 |
| 为什么还要重新校验？ | 预览和提交之间其他管理员可改变目录；真实测试在预览后创建同名内容，提交拒绝且第二行没写入 |
| 注销只是前端退出吗？ | 数据库禁用并逻辑删除、清资料/偏好、全部Redis会话撤销，两个设备旧access/refresh都不能使用 |
| 为什么保留历史和用户名？ | 保持业务关联和统计一致、阻止旧用户名接管；页面提前告知，这是关闭账号，不是物理抹除所有历史 |
| 与预约/刷新同时发生怎么办？ | 同一账号行锁协调顺序，最终不会留下已关闭账号的新有效会话或未结束新预约；有实际并发响应和SQL/Redis证据 |
| 如何证明完成？ | 最终114项HTTP/SQL/Redis、28项真实Edge页面、75/140项回归、48项Maven和前端构建；证据记录实际值及清理，未扩大到生产或模型质量 |

新功能仍有运营大屏、角色调整、提示词版本管理、模型/向量等后续任务；本批不把基础工具完成解释为整个项目所有功能完成。先审核本批PR，再按用户确定的下一项从最新main建立新分支。
