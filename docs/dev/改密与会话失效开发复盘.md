# 改密与会话失效开发复盘

本批完成“密码修改后，旧会话不能继续使用”的真实验收，并修复前端预期错误产生未处理异常的问题。用户改密失败时保留表单与登录；成功后退出并看见重新登录提示。同账号其他设备下次访问时被拒绝，其他用户不受影响。具体响应和失败过程见[接口实测](改密与会话失效接口实测.md)。

## 后端为什么能让JWT提前失效

JWT签名和过期时间本身无法感知用户刚刚改过密码。项目在Redis存会话白名单，每次认证同时检查数据库用户状态、当前密码散列对应的指纹，以及JWT里的sid/version是否与会话记录相符。

Redis键为`trip:auth:session:{userId}:sid`，值为“当前BCrypt密码散列的SHA-256指纹 + version”。JWT带userId、type、sid、version等身份信息，不带密码或这个服务端指纹。新登录生成独立sid，因此同一用户可以有多个设备会话。

改密事务写入新的BCrypt散列。下一次使用旧token，服务端用当前散列计算出的指纹和Redis旧会话值不同，即使JWT尚未到期也拒绝认证。刷新同样比较当前指纹，所以不能用旧refresh获得新access。旧Redis键可以保留到TTL到期，它们已经不可用；失效不依赖扫描并删除所有设备的键。

BCrypt每次生成新盐。即使后来把明文密码改回最初内容，散列也不同，最初会话不会重新变有效。本次专门验证了这个场景。认证会查询数据库/Redis，不能将本方案误称为完全无状态JWT。

## 并发改密和刷新分别怎么处理

改密先验证旧密码，再执行带旧散列条件的更新：只有`id`、`password`、账号有效状态仍符合读取结果时才更新。两个请求若都读到旧散列，先提交者改变它，后提交者更新行数为0并返回冲突，不会悄悄覆盖先提交的新密码。

刷新通过Redis Lua原子比较和替换version：旧值相同才轮换并更新TTL。两次同refresh请求只有一个成功。后端原子性与前端多标签页协调是不同问题，本批只实测后端竞争以及改密退出的跨标签页传播，未完成同时刷新时的浏览器协调。

## 为什么请求层提示后页面还要catch

Axios拦截器负责统一提示并将请求置为失败，这样页面不会误执行成功分支。但Promise拒绝仍会传播到调用方；只有`finally`只能恢复loading，不能处理拒绝。本次实际观察到错误旧密码、相同密码、过期会话读取和旧密码登录产生4个浏览器未处理异常。

在资料加载、改密和登录入口增加catch，让已提示的业务失败在页面结束传播；finally仍负责恢复按钮。成功分支清空密码输入、清除本地access/refresh/用户信息，用路由replace进入登录页，提示无需随整页刷新消失。进行中保护防止重复触发同一提交。

## 答辩复盘要点

- 区分三个层次：密码校验和数据库更新、服务端会话失效、浏览器本地登录状态清理。
- 区分HTTP状态和业务code：旧access在过滤器返回HTTP401，旧refresh在控制器返回HTTP200/code401；验收同时检查。
- 区分“拒绝后续请求”和“撤回已在执行的请求”：改密不主动中断已通过认证的在途操作；其他设备没有推送通知，在下一次请求时发现失效。
- 用实际证据解释保证范围：75项HTTP/SQL等检查、24项浏览器检查与已有功能回归；两请求竞争不等于生产压力测试。
- 保留测试缺陷：前两轮浏览器响应体读取时序失败，以及HTML误匹配，不能把它们说成后端改密失败；这两项已在实测中单独记录。
