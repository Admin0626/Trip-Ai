## 覆盖场景

注册不填写邮箱仍可用；填写时必须消费正确注册验证码并持久验证标记。邮箱规范化，数字验证码JSON/非法邮箱/额外字段拒绝，普通资料写接口不能跳过验证。SMTP接收实际邮件，6位验证码不出现在HTTP或Redis明文；TTL为600秒，已消费码、重发旧码、强制过期码及错5次后正确码拒绝。

同一重置码两个并发请求只成功一次。旧密码登录失败，两设备旧access和refresh均被拒绝，新密码可登录；重置不会自动创建登录会话。未注册/未验证/禁用邮箱走相同邮件路径及响应，不能重置账号。邮箱绑定码按本人隔离，已占用邮箱冲突；旧账号验证后可恢复，更换邮箱或改密后此前恢复码无效。SMTP拒收清理挑战并释放本次冷却；同邮箱、IP、全站小时限制实际拒绝。

页面通过注册发送/倒计时/地址变更清空验证码、当前密码错误、本人绑定/更换、刷新验证状态、资料正常保存、忘记密码入口、确认密码不一致、错误验证码保留草稿、SMTP失败后重试、成功后登录以及两设备失效检查。390px手机布局无横向溢出，截图：[恢复页](evidence/email-auth/2026-10-01T13-45-44-379Z-browser/recovery-mobile.png)、[个人中心](evidence/email-auth/2026-10-01T13-45-44-379Z-browser/verified-profile-mobile.png)。

## 首轮失败与修正

- [首轮接口75/80](evidence/email-auth/20261001-212830-http.json)：独立场景反复使用一个地址，触发真实每小时5次限额；已占用邮箱先返回409，测试却预期跨用户400。修改脚本，只重置专属fixture地址预算来分离边界场景，保留最后的真实小时限额检查；新增未占用邮箱的跨用户码隔离用例。不是取消产品频率限制。
- 代码审查发现注册DTO可能将数字JSON验证码转成字符串；加严格反序列化并在最终接口加入400检查。
- [首轮页面19/21](evidence/email-auth/2026-10-01T13-34-53-892Z-browser/results.json)：多个加载遮罩导致strict locator歧义；改为等待所有遮罩移除。Windows Redis CLI多行CRLF未拆净，部分测试键删除遗漏；改用CRLF兼容拆分，并按原报告唯一邮箱标识恢复清理。[恢复记录](evidence/email-auth/browser-cleanup-recovery.json)：删除1个残留测试键，最终0残留。恢复脚本初次默认GBK读取UTF-8、随后把空KEYS返回当成键，均在写入/删除前停止，修正编码和空行后完成。
- 新工作树的依赖安装需要沙箱写权限；经自动审批后完成，没有更改应用邮件凭据。Git原配置指向未运行的本机代理；交付命令临时取消代理，未修改用户Git全局配置。

## 清理与边界

最终接口账号/会话/邮件挑战和页面账号/会话/邮件挑战清理检查全部通过。SQL只删除脚本建立的唯一标记账号，Redis只操作隔离6387端口的fixture键，测试邮件在loopback进程内清除，没有清空业务Redis或重建数据库。证据不保存密码、验证码、令牌或邮件正文。

真实SMTP供应商鉴权/TLS、实际收件、垃圾邮件及生产负载未验收。默认邮件关闭7/7验证的是HTTP暂不可用行为；83/83与33/33验证的是本地协议与业务链路，不能当成真实投递成功。部署、契约及并发设计见[使用与开发文档](邮箱验证与找回密码使用与开发文档.md)。
