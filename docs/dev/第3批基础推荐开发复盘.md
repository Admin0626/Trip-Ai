# 第3批基础推荐开发复盘

## 交付效果

登录用户现在可以从导航“旅行推荐”或首页“按需求找路线”进入`/recommend`，描述需求、检查并编辑解析结果、明确确认后查询已有路线，看到匹配理由并进入路线详情。本阶段没有连接模型，来源与限制均在接口和页面表达。

## 后端如何匹配

MatchController沿用现有JWT鉴权，不允许游客访问。MatchCriteria保留JSON原始类型，严格检查整数、列表、标签、范围与互斥条件；这避免重复上一阶段“数字自动变字符串”的类型边界问题。

MatchService执行只读事务，通过JdbcTemplate参数化查询：route与destination联表，只允许双方status=1且deleted=0。多目的地内部用OR，目的地/天数/预算/排除标签之间用AND。先COUNT得到全部满足硬条件的数量，再按偏好命中数、用户评分和ID排序，取topN。每个用户字符串都是占位参数，只有固定SQL片段参与拼接。

偏好是软条件：即使没有命中标签，路线只要满足硬条件仍可返回。排除标签是硬条件，因此偏好与排除重叠必须报错，不能一边加分一边过滤。数据库标签使用FIND_IN_SET完整项匹配，不用LIKE模糊匹配。评分相同以ID稳定排序，避免每次刷新顺序漂移。

recallScore只是偏好命中比例，llmScore=null，source=RULE_BASED；总数不随topN变化。未支持的非空字段进入unsupportedCriteria，不能假装已按月份或节奏筛选。没有发生模型调用，所以不向llm_call_log伪造调用记录。

## 前端如何避免过期结果

页面状态分成原始query、可编辑intent和已匹配results。编辑原始query会清掉旧intent，编辑intent或目的地文本会清掉旧results。每次修改增加revision；发请求时捕获revision与条件快照，响应返回时只有版本仍一致才更新页面，离开页面也使旧版本失效。

这样解决了“用户在等待期间改了预算，旧请求回来却显示旧预算的路线”的竞争问题。浏览器测试延迟真实请求，修改条件后检查旧响应确实未展示。按钮提供loading反馈，错误提示允许重试，未知数值清空后规范为null，避免输入框undefined导致协议漂移。

## 答辩解释

可以这样描述：“我把旅行推荐先拆成可靠的基础链路。规则解析只给出初步条件，用户确认后才筛选真实在架路线。硬条件保证目的地、天数和预算符合，软偏好用于排序。接口返回可解释的命中理由，并明确哪些条件未使用。后续模型只增强解析和排序，当前链路能作为降级基础。”

实测价值不只是通过计数：接口用隔离的8条路线和3个目的地验证删除/下架隔离和排序优先级；浏览器验证确认步骤、登录回跳、空结果、错误恢复和异步竞争。手机截图发现仅检查“无横向滚动”仍会漏掉文字竖排，因此补充视觉检查和导航高度断言。详见[接口与页面实测](第3批基础推荐接口与页面实测.md)。

## 待办与取舍

当前目的地按数据库原名精确匹配，不做别名或语义消歧。复杂条件没有对应结构化数据，不能编造匹配理由。小数据集用联表和FIND_IN_SET实现，未来数据量增大应将标签规范化并增加索引/缓存，再做负载测试。

下一任务建议增加推荐请求配额与统计，让基础链路具备限流提示和可观察的调用情况；真实模型继续按用户要求暂缓。模型客户端、数据库提示词渲染、Schema和重试仍是独立待办，多路召回、模型重排、SSE、RAG也未交付。
