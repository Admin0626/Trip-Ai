# 本地知识维护与检索质量开发复盘

2026-10-02。已合并的知识功能能维护资料和逐篇重建，本批补上管理员整体健康统计、异常筛选和有界批量修复，同时解决真实评估复现的来源挤占与首摘录质量问题。页面仍`/admin/ai/knowledge`，用户检索入口`/knowledge`与私人历史`/ai/chat`。

## 演示顺序

管理员查看资料总数、可检索数、索引就绪/异常、来源未公开和待关联来源；筛选异常索引→选中资料→确认修复→查看逐项结果。健康项保持原分片，版本冲突提示刷新，停用项修复后仍停用。来源未公开需要检查目录上下架，旧资料无来源ID需要人工关联。

用户用相同关键词搜索多个来源，前几个结果优先来自不同资料；长资料在文末提及问题时，优先展示实际正文命中的分片。每个结果仍是原文片段，标明完整来源，不生成模型答案。

## 元数据就绪为什么不够

原判定只检查index_method和indexed_revision。如果分片因维护错误丢失，仍能公开全文，却无法真正检索；分片代次损坏也需要可解释的维护入口。本批就绪条件增加实际非空、数量一致、代次一致，并共用于后台状态、检索、全文和历史引用核验。

健康统计是数据库快照，刷新取得当前状态，不是后台常驻监控。只检查结构，不逐词重算所有倒排项或验证正文校验和；大型库需再评估查询计划、数据量与成本。来源无ID的旧文档继续兼容全文，本批只提醒人工补关联，不推测业务ID。

## 为什么批量不包在一个大事务里

管理员可能同时选中健康、异常、被另一窗口编辑、已经删除的资料。整体回滚会让一篇冲突阻止其余合法修复。本批先验证参数及重复ID，每篇调用另一个Spring服务的@Transactional方法，锁文档、比较expectedRevision、检查当前结构、执行修复，事务退出后再处理下一项。

KnowledgeMaintenanceService本身不加事务；knowledge.repair经代理生效，内部调用rebuild在已有事务里执行。部分成功需要明确展示，不能只看外层code200就宣称全部成功。版本409/不存在404和其他异常安全503逐项返回，不把SQL或异常堆栈泄漏给用户。

健康资料跳过很关键：每次主动重建都会生成新chunk ID，旧历史引用可能失效。新增repair在健康状态返回UNCHANGED，保持历史引用，也使两个相同版本并发修复一异常文档时得到一REPAIRED、一UNCHANGED。修复不改变状态或来源。原“重建分片”按钮仍是主动重建，有意重建和异常修复分开使用。

## 检索质量如何改进

标题词存在每一个分片的倒排项里，标题命中时无关首片可能与实际正文命中片同分。本批在原覆盖率排序后增加正文命中词数，最后用chunk ID稳定排序；候选正文只计算一次。随后先选择每篇文档最好的分片，数量不足topK再补其他分片。

保留原query/mode/references和keywordCoverage契约，未新增假的语义分数。最多200候选/5结果，阈值0.3；候选池过大时仍可能漏来源。固定3正例的来源召回0.8333→1.0、MRR保持1.0，文末关键词首摘录改好；小样本证据不能外推生产或语义能力。

## 邮件集成与验证边界

同步main时还获取到已合并的邮箱验证/找回密码，SMTP默认未配置。运行服务整体健康DOWN，日志证实MailHealthIndicator探测失败；改用TRIP_MAIL_ENABLED控制健康探测，默认关闭时UP，发送接口仍503、不预留验证码或邮件额度。开启邮件时仍保留SMTP健康检查，但本批没有配置真实供应商或验证开启后的真实投递。

已有邮箱隔离测试默认指向8087/Redis6387，环境没运行，留下0项INCOMPLETE；不能把它当通过。本批实际8080/6379验证默认关闭行为及账号认证，保留端口错误记录。原知识129项、私人历史146项、认证75项、基础21项回归通过，40项Maven测试和生产构建通过。
