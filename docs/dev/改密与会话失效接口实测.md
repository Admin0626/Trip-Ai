## 真实接口范围

- 普通未登录请求、把refresh当作access的请求均不能改密。
- 旧密码错误、新旧相同、新密码不足8位/超过20位、纯数字/纯字母/空白、缺字段、数字/null/数组类型、多传他人userId均拒绝；失败不改变数据库密码，也不撤销有效会话。
- 8位和20位合法新密码均能修改并登录；验证数据库使用BCrypt，成功后散列改变，不记录散列内容。
- 同一账号在两台设备各持有独立会话，其中一台提前刷新过令牌。改密后原始pair、刷新后的pair均不能访问受保护接口，也不能再刷新。其他用户的access和refresh正常。
- 旧密码登录失败，新密码登录及新会话刷新成功。再把密码设回原始明文，最早的旧token仍无效，新BCrypt盐不会让旧会话复活。
- 同时发起两个改密请求，实际一方成功，另一方业务409；胜出密码可登录，落败密码不能登录。两个旧pair均失效。
- 同时用一个refresh发起两次刷新，实际一方业务200、一方401；胜出pair可访问，原pair不能访问或再次刷新。
- 新登录退出后，当前pair的access和refresh均失效。最后清理3个临时账号与各自Redis会话键。

这只验证了本机两个请求竞争，不等于生产压力测试；并发改密的失败请求可能因调度先后在认证或旧密码校验阶段被拒，脚本允许401/400/409但严格要求只有一个成功。

## 实际响应示例

以下摘录省略 `timestamp`；完整HTTP状态和响应体在JSON证据中。

| 操作 | HTTP状态 | 业务响应 |
|---|---|---|
| 错误旧密码改密 | 200 | `{"code":400,"message":"原密码不正确","data":null}` |
| 新旧密码相同 | 200 | `{"code":400,"message":"新密码不能与原密码相同","data":null}` |
| 合法改密 | 200 | `{"code":200,"message":"success","data":null}` |
| 改密后旧access读取资料 | 401 | `{"code":401,"message":"未登录或登录已过期","data":null}` |
| 改密后旧refresh刷新 | 200 | `{"code":401,"message":"未登录或登录已过期，请重新登录","data":null}` |
| 旧密码登录 | 200 | `{"code":1001,"message":"用户名或密码错误","data":null}` |
| 并发改密落败者（本次） | 200 | `{"code":409,"message":"账号已发生变化，请重新登录后重试","data":null}` |

注意项目现有协议：JWT过滤器拒绝access使用HTTP401；控制器中的刷新拒绝沿用HTTP200/业务401。本批未改响应协议，前端已同时处理两类401。旧实测文档将refresh拒绝笼统称为HTTP401的表述已修正。

## 发现的问题、原因与解决方案

| 编号 | 问题与证据 | 原因 | 处理及验证 |
|---|---|---|---|
| PW-01 | 浏览器实际产生4个pageerror：旧密码错误、密码相同、其他设备会话过期、旧密码登录失败 | 请求拦截器显示错误后继续reject，页面异步事件/加载钩子只有finally，没有catch | 在Profile资料加载/改密、Login提交入口捕获预期失败；保留拦截器提示，不重复弹窗。最终24项通过且pageerror=0 |
| PW-02 | 改密成功后使用`location.href`整页导航，成功提示随页面销毁 | 成功提示与硬跳转放在同一调用链 | 清空表单和认证存储，用`router.replace('/login')`切换，保留“密码已修改，请重新登录”；补断言确认提示可见，保护路由不可回访。增加进行中保护防重复提交 |
| TEST-01 | 前两轮成功改密后Playwright报`No resource with given identifier found` | 页面整页导航销毁原响应资源，回读JSON时已不可用；提前发起读取也未稳定解决 | 浏览器成功请求取HTTP状态，并用跳转、新密码登录及旧会话失效验证结果；完整JSON由HTTP脚本保存，不伪造响应 |
| TEST-02 | 完整基线中“旧access拒绝”读到200，但API实际拒绝 | `endsWith('/user/profile')`同时匹配HTML页面和`/api/user/profile` | 精确匹配API pathname；最终捕获真实HTTP401 |

## 浏览器实际流程与证据

使用两个隔离BrowserContext模拟两台设备，并在第一设备打开第二标签页。依次验证两次密码不一致时不发送HTTP、错误旧密码与相同密码提示、失败保留登录态、改密成功、认证存储清空、同浏览器标签页感知退出、第二设备请求401并刷新失败后退出、旧密码拒绝、新密码登录成功及密码表单为空。

- [手机改密截图（密码字段遮罩）](evidence/password/2026-09-27T14-22-03-976Z-final-browser/password-mobile.png)
- [重新登录后的资料页](evidence/password/2026-09-27T14-22-03-976Z-final-browser/profile-after-relogin.png)

不同设备不会收到服务端主动推送退出通知，下一次受保护请求时才清除本地状态。同浏览器标签页通过storage事件同步。这里没有模拟两个标签页同时触发前端刷新请求，不能据此认定跨标签页刷新协调已完成。

## 复现

先按根README启动MySQL、Redis、后端与前端。Python脚本仅用标准库，需PATH中的mysql/redis-cli；`MYSQL_PASSWORD`可覆盖本机开发密码。Edge脚本沿用项目已有Playwright运行时，可用`PLAYWRIGHT_MODULE`覆盖。

```powershell
# trip-server
python scripts/password_acceptance.py --label final
python scripts/basic_user_acceptance.py
mvn test

# trip-web（前端5173已启动）
node scripts/password_browser.cjs --final
node scripts/avatar_browser.cjs
npm run build
```

本批脚本只清理明确创建的用户及该ID对应的Redis会话前缀。原始服务日志不提交。管理员写操作、下架内容隔离及其他新页面仍未由本批验收，下一批优先管理员反馈处理。
