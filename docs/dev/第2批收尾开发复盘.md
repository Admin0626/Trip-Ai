# 第 2 批收尾开发复盘与答辩提纲

> 本文配合《第2批接口实测与缺陷修复记录》使用。接口结果、修复前后响应和截图以实测证据文件为准；本文负责解释设计、代码结构和答辩表达。

## 一、这一批交付了什么

第 2 批把“能浏览路线”扩展成“能参与和规划”：用户可以点赞、收藏、预约路线、发表评论和回复，也可以创建、编辑、拖拽、复制、导出自己的多日规划。管理端可以查看预约、审核预约状态、隐藏评论和查看路线互动统计。前端完成了用户端路由、请求封装、登录守卫、路线详情、预约评论区、收藏/预约列表和规划编辑器。

当前明确的边界是：评论情感分析、AI 行程优化、AI 推荐和 AI 问答仍属于第 3 批；本批评论的 `sentiment` 写入 `unknown` 是有意保留的接口契约，不是漏做。

## 二、后端请求链路

```text
HTTP Controller
  → 参数校验（Jakarta Validation）
  → 当前用户 / 角色识别（JWT）
  → Service 归属校验与业务规则
  → MyBatis-Plus Mapper
  → 事务提交
  → R<T> / PageResult<T>
```

点赞、收藏、评论点赞和预约审核先锁路线行，再读取明细，最后原子更新路线冗余计数。这样多个请求竞争同一条路线时，检查、明细变更和计数更新处于同一事务内。规划保存则使用“先删旧 item、再删旧 day、重新插入”的整体替换策略，服务端按数组顺序重新生成 `dayIndex` 和 `sortNo`，不信任前端传来的排序编号。

## 三、为什么这样设计

### 1. 为什么计数保存在 route 表

路线详情页一次要展示点赞、收藏、预约、评论和浏览量。如果每次都实时聚合明细表，会增加查询和联表成本。冗余计数适合读多写少的详情页；代价是每次写操作必须在同一事务里同步更新，并用唯一键、路线锁和原子加减维护一致性。

### 2. 为什么预约提交和管理员确认都校验名额

提交时的订单默认是待确认，不应占用已确认名额；管理员把订单改成已确认时才真正占用名额。因此两个入口都必须计算：

```text
当前已确认人数 + 本次 peopleNum ≤ quota_per_day
```

锁住 `route` 行后再计算，两个并发审核就不能同时读到同一个剩余名额。答辩时可以用“3 个名额、两个各 2 人订单”说明为什么只能确认一个。

### 3. 为什么规划保存整体替换

拖拽可能同时改变天数、天内顺序、删除和新增。差量更新要处理大量分支，容易残留孤儿 item 或触发唯一键冲突。演示规模下整体替换更容易保证状态一致：旧 item → 旧 day → 新 day → 新 item，全部放在一个事务中。

### 4. 为什么归属校验在 Service

Controller 只能知道当前用户和请求 ID，不能把“这个 ID 是否属于当前用户”的判断散落到每个接口。所有规划和预约的更新、删除、详情读取都进入 Service 做 `id + userId` 校验；查不到就返回 403。这样可以防止用户 A 操作用户 B 的规划或预约。

## 四、前端如何与后端保持一致

请求拦截器从 `trip_token` 读取 JWT，统一添加 Bearer 头；收到 401 时清理本地登录信息并跳转登录页，403 显示无权限。页面只接收后端 `data` 中的业务对象，分页统一使用 `records/total/current/size/pages`。

规划编辑器使用天 Tab 和可拖拽列表。服务端仍是排序最终权威：保存时前端发送数组，后端重新编号。编辑器保存后回到规划列表，模板创建会把地址规范化为 `/plan/{id}/edit`，避免刷新创建重复规划。详情页的路线标签按后端实际 `string[]` 处理；评论区接入回复、删除、点赞、分页和图片回显。

## 五、验收路径（答辩现场可复述）

1. 用普通用户登录，打开路线详情，展示点赞、收藏和登录态回显。
2. 提交预约，进入“我的预约”，说明待确认状态；管理员将其确认，再演示非法状态流转被拒绝。
3. 回到路线详情发表 5 星评论，回复评论，再删除自己的评论；普通用户不能删除别人评论。
4. 打开规划编辑器，创建 5 天行程，拖一项到另一天，保存后刷新，展示天数、顺序、摘要、住宿、用餐和预算保持一致。
5. 打开景点抽屉，从 `GET /destination/{id}/attractions` 添加景点；复制规划后说明副本是草稿；导出得到文字行程单。
6. 打开接口实测报告，展示并发名额、每日评论上限、50 条规划上限、越权和参数异常的真实响应。
