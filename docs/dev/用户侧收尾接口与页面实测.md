# 用户侧收尾接口与页面实测

日期：2026-09-28（北京时间）。起点783b0e4。范围：个人统计、保存偏好参与基础推荐、跨标签页刷新，以及偏好/目的地详情页面。本报告来源于实际运行的Spring Boot、MySQL、Redis和Edge；没有虚构接口响应，也没有调用真实模型。

## 环境与方法

后端8080/api、前端5173（Vite代理）、MySQL3306、Redis6379。Java按17目标编译，本机JDK21/Maven3.9.14；浏览器为Playwright驱动的真实Edge。接口验收用Python标准库HTTP；仅SQL创建明确的临时目录内容和部分统计夹具，HTTP完成偏好、推荐、互动及统计操作。页面验收实际填写、点击并读取服务响应。

多页测试属于同一浏览器上下文、同源localStorage，四个真实401响应在屏障处等待后同时释放。测试把access设置为无效值、保留真实refresh令牌，触发真实后端旋转；不是等待自然到期，不合成刷新响应。竞态测试暂停真实刷新响应的交付，期间清除本地会话、换账号或同账号重新登录，然后释放响应。离线/route.abort仅用于制造传输故障。

接口次数包含夹具、业务断言和清理检查；不是63个不同端点。浏览器次数包含UI、HTTP及清理断言。真实模型质量、负载和所有浏览器不属于这次结论。

## 实际接口响应与行为

临时用户保存常用3天、人均预算150.50—300.50元、偏好海滨/康养、排除探险。六条临时路线分别为：3天200.50元海滨/康养；3天250元自然风光；3天150.49元海滨；3天300.51元海滨；5天200元海滨；3天240元海滨/探险。

`POST /ai/recommend/match`传`{"intent":{"destinations":["临时目的地"]},"topN":20,"useSavedPreference":true}`，实际HTTP200/code200，totalCandidates=2，200.50元路线先于250元高评分路线；前者recallScore=1，后者0，llmScore均null。最终响应data的条件部分如下（临时目的地名称省略，完整响应在JSON）：

```json
{
  "source":"RULE_BASED",
  "effectiveCriteria":{
    "days":3,"budgetMin":150.5,"budgetMax":300.5,
    "preferenceTags":["海滨","康养"],"avoid":["探险"]
  },
  "savedPreferenceFields":["days","budgetRange","preferenceTags","avoid"]
}
```

关键实际检查：

| 请求或操作 | 实际结果 |
|---|---|
| false/省略useSavedPreference | 六条夹具均参与候选；旧调用行为保持 |
| 另一个没有偏好的用户选择true | 六条候选，不继承第一个用户设置 |
| 顶层伪造userId | 仍用token身份的偏好 |
| 明确days:null、budget:null、标签[] | 六条候选；清空不会补回默认值 |
| 明确days:5及空标签/清空预算 | 仅5天路线 |
| 150.50—200.50且3天 | 只命中200.50元，含上边界，不含150.49元 |
| 上下限均200.50 | 精确命中200.50元路线 |
| 仅明确预算上限200.50 | 不继承保存的下限，包含150.49元路线 |
| 明确偏好探险或带空白的` 探险 ` | 冲突的保存避雷移除，探险路线排在前面 |
| 明确排除海滨或` 海滨 ` | 覆盖保存的冲突偏好，仅自然风光路线留下 |
| useSavedPreference:"true" | HTTP200/code400，提示JSON布尔值 |
| 区间数字字符串、布尔值、三位小数或下限大于上限 | HTTP200/code400 |
| 保存8个标签并用于match | 两个接口均HTTP200/code200 |
| 未登录读stats/preference | HTTP401/code401 |

`GET /user/stats`在实际创建收藏、预约、评论、规划后响应为：

```json
{"code":200,"message":"success","data":{"favoriteCount":1,"bookingCount":1,"commentCount":1,"planCount":1,"chatCount":0}}
```

四项在页面显示为1；另一个用户全部0；userId参数不能切换统计对象；删除本人评论后commentCount=0。预约统计含取消/完成记录；评论与规划排除逻辑删除。规则匹配没有新增模型日志。UI中解析需求本身会产生既有rule-only降级日志，不能将整个UI流程误称为零日志。

页面还实际验证：统计断网提示/重试、无效手机号code400且无pageerror；偏好非法范围本地阻止、两位小数保存及重载；偏好读取失败禁用保存、恢复后可编辑；推荐未知项预填、开关关闭、全部手动清空、明确5天/500元/美食覆盖保存默认值；目的地只显示在架景点和路线，下架父目的地后旧详情消失，恢复后重试成功。

## 产品缺陷、原因与修复

| 编号 | 发现的问题与证据 | 原因及解决方案 |
|---|---|---|
| U-01 | 个人中心没有统计卡片，已有stats接口未被页面调用 | 接通4项个人记录及相应列表入口，提供独立加载/错误/重试，不把未完成对话产品展示为可用 |
| U-02 | 基线设置偏好后仍返回6条路线，未使用天数、预算、排除和排序偏好 | MatchController只用请求intent。增加认证身份驱动的PreferenceMatchService及明确的opt-in；页面预填并显式确认，服务端返回实际条件/默认来源 |
| U-03 | 新预算区间被忽略，非法值也code200；传150.50—200.50仍按旧整型预算处理 | 旧MatchCriteria仅支持整数budget。增加严格小数区间校验及参数化价格过滤，保留旧budget契约 |
| U-04 | 设置允许的标签与推荐词表不一致，8标签无法跨接口使用 | 后端统一TravelTags21项，前端共用travelTags；匹配偏好上限扩至8。保留保存避雷5项和匹配排除21项的不同用途 |
| U-05 | 两页发出2次刷新，一次CAS失败后两页登录都被清除 | 页内Promise只能协调一个页面。Web Locks按同源串行刷新，锁内重读最新整组令牌，晚到401重用已更新令牌；原子存储防止混合令牌对 |
| U-06 | 原恢复流程缺少退出/换账号/同账号重登录后的在途响应保护 | 添加epoch与用户校验，刷新保持epoch，新登录换epoch。重放与成功响应也校验epoch；网络错误保留会话，真实401只撤销仍对应的旧会话。此项属防护补强，未声称基线逐项复现所有竞态 |
| U-07 | [边界扩展59/63](evidence/user-finish/20260928-215017-852540-final.json)：带首尾空格的明确标签无法覆盖保存冲突标签 | 合并时先比较原字符串，MatchCriteria之后才strip。冲突合并先规范化明确标签，再保留最终严格校验；最终63/63 |
| U-08 | [会话扩展28/29](evidence/user-finish/2026-09-28T14-06-53-235Z-final-refresh/results.json)：跨页换账号后，资料表单仍是旧用户内容 | store只同步菜单资料，已挂载的表单没有重新读取。App按epoch重新挂载路由页面，刷新epoch不变不会重挂载；退出受保护页跳登录，失去ADMIN身份离开后台。最终30/30中实际核对新昵称及两页退出路由；改密24项、用户页41项、后台50项再次通过 |

兼容补强：登录epoch生成在randomUUID不可用时使用独立随机会话标记，实际关闭randomUUID后仍能认证；这个标记不承担令牌签名功能。无Web Locks时提示重新登录，不冒险刷新。

## 测试/采集问题与恢复

1. [第一次接口18/22](evidence/user-finish/20260928-211720-287409-baseline.json)：合法新区间被旧接口拒绝后，脚本直接读取null data引发TypeError，中断后续项目。改为记录空结果继续断言，完整基线33/44保留。
2. [刷新0/1](evidence/user-finish/2026-09-28T13-27-20-492Z-final-refresh/results.json)：Maven编译引发运行服务DevTools重载，注册响应为空，JSON解析中断；查库无该临时账号。后续编译与验收分开、健康UP后执行，注册前先记录生成的用户名以便恢复清理。
3. [用户页23/24](evidence/user-finish/2026-09-28T13-33-37-007Z-pages/results.json)：Element Plus原生checkbox隐藏，Playwright原生uncheck等可见失败。改点可见label并断言isChecked；产品开关可用。
4. [原推荐22/23](evidence/batch3-match/2026-09-28T13-40-35-987Z-browser/results.json)：预算两位小数使显示由3000变为3000.00，字符串断言过严。改按数值比较，23/23。
5. [第一轮通过截图](evidence/user-finish/2026-09-28T13-37-04-349Z-pages/recommend-mobile.png)保留：手机尺寸切换后直接全页采集，浏览器在旧滚动位置绘制sticky导航，部分控件绘制未稳定。改为失焦、滚动顶部并等待稳定后重新采集，人工核对没有上述异常；不把采集伪影当作产品CSS缺陷。
6. 本机旧Windows redis-cli的`--scan`静默空输出，旧清理断言不成立；实际`SCAN 0 MATCH ... COUNT ...`发现残留。新增Python/Node显式游标循环，限定单个夹具用户前缀、删除后复扫，并持久记录夹具ID。既有改密、头像、反馈、后台及原推荐脚本也改为共用扫描器，避免同类问题再次出现；实际回归如上。
7. 新Python扫描器首轮把Redis空数组表示的空行当成异常键：[54/55](evidence/user-finish/20260928-214654-346467-final.json)、[改密72/75](evidence/password/20260928-214657-260100-final.json)、[原匹配中断证据](evidence/batch3-match/20260928-214703-891239-http.json)。最后一份记录已完成业务断言，但在清理处异常，缺最终清理断言，不当作完整通过。修正空行解析；[该轮夹具恢复](evidence/user-finish/fixture-recovery.json)核对两账号、临时目的地/路线及会话已清理。
8. [退出路由扩展10/11](evidence/user-finish/2026-09-28T14-08-27-013Z-final-refresh/results.json)：直接导入无版本的storage.ts测试方法，与Vite热更新后页面实际导入的模块URL可能不同，产生独立的监听器集合。跨页storage事件仍生效，但当前测试页的手动clearAuth没有通知页面监听器，等待路由超时。脚本改为从页面资源记录解析实际storage模块URL并复用；最终30/30。实际改密/退出页面回归使用产品按钮，不依赖该测试导入方法。

清理核实：[恢复记录](evidence/user-finish/redis-cleanup-recovery.json)对证据可确认且账号已删除的58个临时用户复核，删除53个历史残留会话，逐个剩余为0；最终新脚本均使用可靠扫描。该修正覆盖本批回归的清理方法，旧基础后台等报告中依赖`--scan`的清理表述应以本记录为准。旧证据没记ID而无法归属的会话保留自然TTL，未清空Redis或撤销现有用户会话；删除账号的令牌本来就被后端拒绝。没有重建数据库，没有修改现有用户数据。

密码/JWT在HTTP证据中脱敏，刷新报告只记录状态码与布尔断言；未存储模型Key、密码散列或原始运行日志。历史失败证据保持不改。

## 复现

按根README启动服务；已有库不要执行schema.sql，本批无SQL迁移。后端在trip-server运行`python scripts/user_finish_acceptance.py --label final`、`python scripts/password_acceptance.py --label final`、`python scripts/batch3_match_acceptance.py`、`mvn test`。先编译再等后端健康UP，然后进行HTTP/浏览器验收。

前端在trip-web运行`node scripts/user_finish_browser.cjs`、`node scripts/refresh_browser.cjs --final`、`node scripts/password_browser.cjs --final`、`node scripts/avatar_browser.cjs`、`node scripts/batch3_match_browser.cjs`、`npm run build`。需mysql/redis-cli可执行，PLAYWRIGHT_MODULE可指定已有Playwright安装，MYSQL_PASSWORD覆盖本机数据库凭据。每轮证据新文件；浏览器输出目录使用UTC时间，HTTP目录使用北京时间。
