## 二、互动模块写什么（INT-01~10）

### 2.1 点赞 / 收藏（BR-INT-01，状态切换）

**表**：`route_like` / `route_favorite`，都有 `uk(user_id, route_id)`。

**最终 Service 逻辑（事务内先锁路线行）**：

当前接口是 toggle：重复请求会再次切换状态，不是严格幂等。不要将超时请求无条件自动重试。

1. `SELECT count(*) FROM route_like WHERE user_id=? AND route_id=?`（或 `selectOne`）
2. 不存在 → `INSERT` + `UPDATE route SET like_count = like_count + 1 WHERE id=?`
3. 已存在 → `DELETE` + `UPDATE route SET like_count = like_count - 1 WHERE id=?`
4. 返回 `{ liked, likeCount }`（likeCount 从 `route.like_count` 读，原子加减后已是最新）

**为什么必须是"先查 + 原子加减"，不是"先查 count 再设"**：
- 计数走 `like_count = like_count + 1` 数据库侧原子运算，**不要** `getLikeCount() + 1` 再 update —— 并发会丢数。
- 唯一键 `uk` 保证同用户同路线不重复记录；最终实现先锁路线行，再查询状态、增删明细、更新计数。旧版只依赖唯一键并捕获异常转取消，在并发取消时已实测失败，不能继续照抄。

**点赞状态回显**（`RouteDetail` 的 `liked`/`favorited`）：`SELECT 1 FROM route_like WHERE user_id=? AND route_id=?` 有则 true。第 1 批 `RouteServiceImpl.detail()` 里 `vo.setLiked(false)` 是写死的 —— **本批要改成查库**（注入 RouteLikeMapper / RouteFavoriteMapper，老接口里一起带上）。

> 改动点：`RouteServiceImpl.detail()`、`RouteServiceImpl.toPageVO()` 里的 liked/favorited 从 false 改为按当前用户查。**这需要拿 userId**：`SecurityContextHolder` 里取 principal（参照 `AuthController.me()` 的写法）。

### 2.2 预约（INT-04/05，BR-INT-02/03/04 —— 本批最容易卡住的点）

**表**：`route_booking`。

**提交预约校验顺序（一条都不能少）**：

```
① 参数校验（DTO @NotNull/@Min 等，交给 Jakarta Validation）
② BR-INT-02：travelDate ≥ 明天（LocalDate.now().plusDays(1)）；peopleNum 1-10
③ BR-INT-03：SELECT count(*) FROM route_booking
             WHERE user_id=? AND route_id=? AND travel_date=? AND status IN (0,1)
             → >0 抛"已预约"（2004/BOOKING_DUP）
④ BR-INT-04 名额（★ 必须行锁）：
   SELECT quota_per_day FROM route WHERE id=? FOR UPDATE
   SELECT COALESCE(SUM(people_num),0) FROM route_booking
         WHERE route_id=? AND travel_date=? AND status=1
   已确认人数 + 本次 ≤ quota_per_day，否则抛 2002 BOOKING_FULL
⑤ 生成 bookingNo：32位随机UUID字符串；唯一索引兜底，前端不解析编号结构
⑥ INSERT，status=0；UPDATE route SET booking_count = booking_count + 1
```

**为什么 `FOR UPDATE` 必须加**：两个用户同时抢最后一个名额，不加锁会都通过校验 → 超卖。演示规模虽小，但这是 BR-INT-04 的标准答法，**答辩必问**。

最终实现先锁路线再查重/检查名额，确认订单人数通过当前读累加。管理员确认也取得同一路线锁并再次检查人数；仅待确认订单不占用已确认名额。`booking_count` 统计状态0/1/3的未取消订单数量，不是总人数。

**取消预约**（`PUT /booking/{id}/cancel`）：
- 归属校验：`booking.userId == 当前用户`，否则 403
- 仅 `status=0/1` 可取消，`status=2` 报"已取消"，`status=3` 报"已完成不可取消"
- 取消后 `UPDATE route SET booking_count = booking_count - 1`

**我的预约列表**（`GET /booking/page`）：`status IN (0,1,2,3)` 全给，按 `create_time` 倒序，前端自己显示状态标签。

### 2.3 评论（INT-07/08，BR-INT-05/06/07/08）

**表**：`route_comment`。

**发表评论校验**：
- BR-INT-05：每人每路线每天 ≤ 3 条（`SELECT count(*) ... WHERE user_id AND route_id AND date(create_time)=today`）；score 1-5 整数（DTO `@Min(1) @Max(5)`）；content 5-500 字（DTO `@Size(min=5, max=500)`）
- BR-INT-06：images ≤ 3 张（DTO 校验 List size）
- BR-INT-07：parentId 需存在且 `parent.parentId == 0`（只允许回复顶级评论，第二层折叠）
- 入库后：`UPDATE route SET comment_count = comment_count + 1`；**avg_score 重算**（`SELECT AVG(score) FROM route_comment WHERE route_id=? AND status=1` 更新 route.avg_score）
- 回复评论：`parentId` 非 0，且 parent 仍 show
- **情感分析（INT-13）是第 3 批**：本批入库时 `sentiment` 保持默认 `unknown`，接口照常返回，别在评论 Service 里调 LLM

**评论列表**（公开）：`GET /comment/page`，参数 routeId + 排序（newest/score）+ **情感筛选**（frontend 用，`sentiment` 字段先备着，第 3 批才有数据）。VO 里带 `userNickname`、`likeCount`、`liked`(当前用户是否点过)、`time`。

**删除自己的评论**（`DELETE /comment/{id}`）：
- BR-INT-08：仅作者本人（`comment.userId == 当前用户`）或 ADMIN 可删
- 用户删 = 逻辑删除（`deleted=1`）；管理员隐藏 = `status=0` —— **两回事，别混**（表里两个字段就是为了区分）

**评论点赞**（INT-10，P2，顺手做）：同 route_like 的幂等开关，表 `route_comment_like`，计数走 `route_comment.like_count` 原子加减。

### 2.4 管理端（INT-06/12，P1，本批可做可不做）

- `GET /admin/interaction/booking/page`：全部预约 + 筛选（状态/路线）
- `PUT /admin/interaction/booking/{id}/status`：审核（0→1/0→2）。**状态流转要按 `08` §2.3 状态机**：`0 待确认 → 1 已确认 / 2 已取消`，`1 → 3 已完成`，已取消不可再确认
- `GET /admin/interaction/stat/{routeId}`：点赞/收藏/预约/评论数 + 平均分，一条 SQL 或两次 count

## 三、规划模块写什么（PLN-01~08）✅ 已完成（2026-09-23）

### 3.1 数据模型（3 张表，对称设计）

```
user_plan（主表）          user_plan_day（天）      user_plan_item（行程项）
├─ id                     ├─ user_plan_id          ├─ plan_day_id
├─ user_id                ├─ day_index (uk with   ├─ sort_no (uk with plan_day_id)
├─ title                    user_plan_id)          ├─ time_point / attraction_id / title
├─ destination_ids(逗号)   ├─ title / summary       ├─ activity / transport / hotel / meal
├─ start_date / days       ├─ create/update         ├─ duration_min / cost / tips
├─ budget / people_num                             └─ create/update
├─ status 0草稿 1已保存
└─ source_route_id
```

### 3.2 保存规划（PLN-01/02/05，BR-PLN-01~04 —— 用"整体替换"）

**核心决策：保存用"事务内先删后插"，不做差量更新。**

```
@Transactional
save(userId, planId, dto):
  ① 归属校验：SELECT ... WHERE id=? AND user_id=?，查不到抛 403
  ② 校验（BR-PLN-01/02）：1 ≤ days ≤ 30；每天 ≥ 1 条 item；startDate ≥ 今天；budget > 0
  ③ 每 50 条上限（BR-PLN-04）：SELECT count(*) FROM user_plan WHERE user_id → ≥50 抛 PLAN_LIMIT
  ④ 更新 user_plan 主表字段（title/destination_ids/start_date/days/budget/status）
  ⑤ 删除该 plan 的旧 user_plan_day + user_plan_item（先 item 后 day）
  ⑥ 按 dto.dayList 重新插入 day + item，sortNo 按"前端传来的数组顺序"重新编号
      （BR-PLN-03：前端拖完后传的顺序即 sortNo，服务端按 list index 重排，别信前端传的 sortNo）
  ⑦ 返回
```

**为什么整体替换**：差量更新要处理"删了哪条、改哪条、挪到哪天"的几十种分支，演示规模下纯属自找麻烦。整体替换代码量小、状态一致，唯一键冲突（`uk_plan_day` / `uk_plan_day_sort`）靠"先删后插"天然避开。

**创建**：`POST /plan` → 先插 user_plan（status 默认 0），再走同上的 dayList 落库。`destinationIds` 规则 `1,2` 逗号拼接存 `destination_ids`。

**以路线为模板**（`POST /plan/from-route/{routeId}`）：
- 读 route + route_day + route_item
- 在事务里：插 user_plan（source_route_id=routeId，title="基于《xxx》的规划"）→ 逐天复制（day_index/title → user_plan_day；item 字段全复制 → user_plan_item）
- 复用整体替换的"按 dayList 构建"逻辑，把 route 转成 dayList 再走同一路径，**别写第二套**

## 五、这一批最容易卡住的 6 件事

| # | 现象 | 原因 / 对策 |
|:--:|---|---|
| 1 | 点赞/收藏死循环或计数对不上 | 没走"先查 + 原子加减"；或者 count 用 `selectCount` 返回 Long 没转 int。**计数一律 `route.like_count ± 1`，不读出来算** |
| 2 | 预约并发超卖 / 谈不出 FOR UPDATE | 名额校验 SELECT 没加 `FOR UPDATE`。检查标准：MySQL 里开两个客户端同时约最后一个名额 |
| 3 | 同一用户重复预约同一路线同一日期 | BR-INT-03 是"Service 查"，**不是唯一索引**。别为了省事加 `uk(user_id,route_id,travel_date)` —— 一个用户取消后再约会撞唯一键 |
| 4 | 保存规划报 `uk_plan_day_sort` 冲突 | 旧 item 没删干净就插新的。确认事务内顺序：**先删 item → 再删 day → 再插 day → 再插 item** |
| 5 | 越权操作成功（用户 A 改了用户 B 的预约/规划） | 忘了 Service 层归属校验。**每个 update/delete 先 `WHERE id=? AND user_id=?` 查，查不到抛 403** |
| 6 | 前端 401 后页面白屏、token 没清 | `request.ts` 响应拦截里 401 必须 `localStorage.removeItem(token)` + `router.push('/login')`；同时 JWT 过滤器抛的 401 不走 `@RestControllerAdvice`（第 1 批清单已讲过），前端要认响应状态码 401 而不是业务 code |

**另外两条 Boot 4 注意事项**（重复提醒，别忘）：

| 项 | 说明 |
|---|---|
| `LocalDate` 序列化 | 预约 `travelDate`、规划 `startDate` 是 `java.time.LocalDate`，默认输出 `"2026-10-01"`，前端不用转。若想统一 `yyyy-MM-dd`，字段上加 `@JsonFormat(pattern = "yyyy-MM-dd")` |
| `@Transactional` 生效条件 | 必须放在 **public 方法**上，且**同类内部调用不生效**（this.save() 调自己类的私有方法会绕过代理）。预约/规划的"多表操作"方法要么放 Service 公开方法，要么拆内部类 |
