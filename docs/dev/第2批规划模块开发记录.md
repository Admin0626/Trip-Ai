## 二、实现的功能与关键设计

### 2.1 保存规划 — BR-PLN-01/02/03 与"事务内先删后插"（核心决策）

**`POST /plan` 创建** 与 **`PUT /plan/{id}` 更新** 共用同一套构建逻辑，统一走"整体替换"：

```
@Transactional save(userId, planId?, dto):
  ① 归属校验：SELECT ... WHERE id=? AND user_id=?（更新/详情/删除/复制/导出用，查不到 403）
  ② 校验（BR-PLN-01/02）：startDate ≥ 今天；正式保存(status=1)必须有 dayList；
     每天 ≥ 1 条 item（DTO 层兜底天数 1-30 / 预算>0 / 人数 1-10）
  ③ 50 条上限（BR-PLN-04）：SELECT count(*) WHERE user_id → ≥50 抛 PLAN_LIMIT(2006)
  ④ 更新/插入 user_plan 主表字段
  ⑤ 删除该 plan 旧 user_plan_day + user_plan_item（先 item 后 day，避开唯一键冲突）
  ⑥ 按 dto.dayList 数组顺序重建：dayIndex 按下标重排 1..n，item.sortNo 按顺序 1..n
     （BR-PLN-03：排序以"前端传来的数组顺序"为准，服务端按 list index 重排，不信前端传值）
```

**为什么整体替换**：差量更新要处理"删了哪条、改哪条、挪到哪天"的几十种分支，演示规模下纯属自找麻烦。整体替换代码量小、事务内状态一致，唯一键冲突（`uk_plan_day`/`uk_plan_day_sort`）靠"先删后插"天然避开。`@Transactional` 只在 public 入口方法（create/update/delete/copy/fromRoute）上，私有构建方法依赖调用方代理事务（同类内部调用不生效的坑）。

### 2.2 以路线为模板（`POST /plan/from-route/{routeId}`）— 复用同一构建路径

- 校验 route 存在且上架（否则 `ROUTE_NOT_FOUND`），不写第二套落库逻辑
- 读 route + route_day + route_item → 在事务里插 `user_plan`（`source_route_id=routeId`、`title="基于《xxx》的规划"`、`days/budget/people_num` 取自 route、`status=0` 草稿）→ 逐天复制（day_index/title/summary → day；时间点/景点/活动/交通/住宿/餐食/时长/花费/贴士 全字段 → item）

### 2.3 其他接口

| 接口 | 功能 | 要点 |
|---|---|---|
| `GET /plan/page` | 我的规划分页 | `status` 可选筛选；**批量一次查 `dayCount`**（每天有行程的天数，前端提示哪天没填项），避免 N 次查询 |
| `GET /plan/{id}` | 详情 | 归属校验后返回完整 `dayList`（含 item 全字段） |
| `DELETE /plan/{id}` | 删除 | 归属校验 + 逻辑删除（deleted=1） |
| `POST /plan/{id}/copy` | 复制（P2） | 深拷贝三张表，title 加"（副本）"，status 还原为 0 草稿 |
| `POST /plan/{id}/export` | 导出文字版（P1） | 纯文本组装：标题 → 日期/天数/预算/人数 → 每天 → 每项 `时间点 标题（活动） ¥花费` |
| `POST /plan/{id}/ai-optimize` | AI 优化（PLN-09） | **第 3 批做**，本批预留路径，归属校验后返回业务码 3001 「AI 优化能力将于第 3 批开放」 |
| `POST /plan/from-route/{routeId}` | 路线模板生成 | 见 §2.2 |

**安全**：`/plan/**` 全部需登录（默认 authenticated），未登录返回 403/401；越权访问他人规划统一 403。
