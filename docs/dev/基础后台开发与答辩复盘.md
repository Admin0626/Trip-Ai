# 基础后台开发与答辩复盘

交付日期：2026-09-28。配合[实际测试记录](基础后台接口与页面实测.md)阅读。

## 完成了什么

管理员访问`/admin`进入独立管理布局，包含8个入口：概览与反馈、目的地与景点、路线与行程、首页轮播、预约管理、评论管理、用户管理、AI调用日志。顶部可返回前台或退出登录。

目的地、景点、路线、轮播均有列表与编辑流程。路线可维护价格、名额、推荐权重、置顶和完整每日行程；支持新增/删除/调整天和条目，保存时自动计算天数与顺序。轮播支持上传图片、排序、跳转类型与生效时间，保存后首页实际读取公开接口显示。预约和评论沿用已有业务接口，补上管理员操作页面；账号管理新增后端分页和启停功能。

## 答辩时如何解释关键设计

**为什么前端守卫之外还要后端权限？** 用户可以绕过网页直接请求接口。前端meta只负责操作体验，Security的`/admin/**`和控制器管理员权限负责真正拒绝越权；测试直接发送普通用户写请求，HTTP403。

**为什么下架不等于不能管理历史业务？** 下架后游客不能读取内容或新增互动，但已产生的预约需要审核、完成或取消，评论也需处理。公开操作使用“路线及目的地均已上架”的校验；历史管理只要求路线存在并加锁，继续执行预约状态机和名额检查。把两个用途复用为同一检查会导致基线中管理员无法操作下架路线。

**如何避免公开入口遗漏下架规则？** 同时检查父目的地和路线。列表/详情/每日行程/评论/互动写入/轮播各有真实负向检查；这比只看下架按钮变色更有说服力。下架目的地时不批量改所有路线status，重新上架父目的地后，仍保持各路线自身原有状态。

**路线行程为什么整体替换？** 编辑器提交一份完整的dayList，服务端事务内重建日程条目，再按数组顺序写dayIndex和sortNo。天数必须等于dayList长度，每天至少一项；关联景点必须属于该目的地且已上架。事务失败不会留下半套行程，条目ID可能变化，前台应重新读取保存结果。

**为什么限制删除？** 目的地仍有路线时拒绝删除；路线出现过预约记录时只允许下架，避免丢失历史业务关联。没有阻塞关联后使用既有逻辑删除。景点删除后已有行程文字快照仍保留，继续编辑时可以改为自定义条目或有效景点。

**账号停用如何立即生效？** 每次认证会读取真实账号状态。启停修改锁定用户行，撤销其Redis会话后更新状态；重新启用也不会复活旧access/refresh。登录使用相同行锁，避免停用清理后并发登录再创建旧会话；Redis故障返回503，使撤销失败不会被当作成功。管理员账号受保护，基础后台不提供角色升级。

**为什么返回用户字段投影？** 用户列表只需ID、用户名、昵称、城市、角色、状态及时间。后端SELECT显式列出这些字段，不把完整实体、密码散列、手机号、邮箱或token返回给页面。AI日志同样只展示脱敏摘要。

**如何处理失败与连续操作？** 写操作禁用重复提交并捕获预期错误，业务错误由公共请求拦截器提示，失败保留表单；删除/上下架/账号启停要求操作确认。查询使用递增请求序号，忽略过期响应，过滤变化回到第一页，删除导致空页时自动回退有效页。目的地选择支持搜索，避免仅加载前一页导致其他目的地无法选择。

**如何证明真的测过？** 出示baseline的95/111，逐项说明旧响应、原因和修复；再展示最终真实HTTP/SQL/Redis证据与Edge流程，而不是只出示编译日志。测试计数包括多种断言，不能宣称139个独立接口。初次浏览器截图的动画问题也保留了采集原因与改进记录。

## 推荐演示顺序

1. 管理员登录后台，展示概览和8个模块入口。
2. 新建目的地、上传封面、上架，新增景点。
3. 创建路线与两天行程，调整顺序，保存并从前台查看。
4. 新增指向路线的轮播，在首页点击验证跳转。
5. 用户预约和评论；后台确认预约、隐藏再恢复评论。
6. 下架目的地或路线，前台隐藏，后台仍能处理历史记录。
7. 停用一个普通测试用户并展示旧会话失效，再启用并重新登录。
8. 查看脱敏日志与反馈，退出后台。

## 边界和后续工作

本批完成基础后台操作闭环，不代表原设计中的所有高级运营功能完成。角色调整、用户删除/密码重置/导出、轮播批量排序、提示词版本管理、批量导入、统计大屏和生产负载仍是后续范围。首页读取当前启用轮播，已经打开的页面需刷新获取新状态。

用户侧个人统计、偏好参与推荐、新增页面进一步验收和跨标签页同时刷新令牌协调仍待继续。真实模型质量、模型故障熔断、SSE/RAG等未在本轮实现；生产前端主包约1.12MB的拆包优化仍待处理。无需本批数据库迁移，不应重新执行schema.sql。
