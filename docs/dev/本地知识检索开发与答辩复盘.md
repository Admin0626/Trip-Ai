# 本地知识检索：使用、开发与答辩复盘

2026-09-29。本批先建立能管理、能检索、能追溯原文的本地知识层，用户已明确暂不接语义向量模型。它为后续RAG提供文档和来源基础，不是已完成的生成式RAG聊天。

## 如何演示

1. 启动MySQL、Redis、后端和前端。已有库执行一次upgrade_local_knowledge.sql（可重复），不重建数据库；详见[实测](本地知识检索接口与页面实测.md)。
2. 管理员进入/admin/ai/knowledge或后台“知识资料”。新建默认停用，填写标题/正文，选择独立攻略或有效目的地/路线；保存自动完成本地分片，检查后启用。
3. 导入接受UTF-8 .txt/.md，最大256KiB；正文最大20000个Unicode字符。导入只存正文，不保留原文件，不访问其中的URL。
4. 普通用户登录，进入导航“旅行资料”(/knowledge)，输入“香格里拉十月”或“洱海骑行”，查看摘录，点击完整资料核对全文、更新时间和版本；有关联的有效来源可进一步跳到目录详情。
5. 管理员停用一篇，用户重新检索或请求详情，资料不再公开。另一个管理员先保存时，旧表单409且保留输入，避免覆盖对方结果。

本机原10篇演示资料已索引，正文保留；它们是演示数据，非已核验的最新旅游公告。旧资料没有真实关联ID时只提供资料全文入口，不根据标题伪造目录链接。编辑这类DESTINATION/ROUTE旧资料须明确选择真实来源，或调整为独立攻略。

## 数据流及文件位置

```mermaid
flowchart LR
    A[管理员新增或导入] --> B[权限 类型 大小 编码 校验]
    B --> C[事务锁定文档及版本]
    C --> D[正文规范化与500字符分片]
    D --> E[MySQL文档 分片 倒排词原子保存]
    U[登录用户输入关键字] --> T[NFKC 中文二元组 英文词]
    T --> E
    E --> V[公开来源与当前索引代次过滤]
    V --> R[覆盖率排序及最多5个原文片段]
    R --> S[完整资料及有效站内来源]
```

后端KnowledgeText处理正文与词元；KnowledgeInput处理严格请求类型；KnowledgeService处理事务、CAS、索引与查询；AdminKnowledgeController和KnowledgeController区分管理与用户入口。SQL升级在trip-server/src/main/resources/sql/upgrade_local_knowledge.sql，新建数据库的schema.sql也同步为29表。

前端api/modules/knowledge.ts封装契约；views/admin/Knowledge.vue是管理页，views/knowledge/Search.vue与Document.vue展示片段和全文；AdminLayout、AppHeader、router接入入口。knowledge_acceptance.py、knowledge_seed_index.py及knowledge_browser.cjs记录真实验收。共享证据写入器补充了无效Unicode的合法JSON转义。

## 为什么这样设计

**持久分片**：knowledge_doc增加source_id、revision、indexed_revision、index_method；新增knowledge_chunk及knowledge_chunk_token。分片按Unicode codepoint计数，每片≤500、步长450，重叠50；start_offset包含起点、end_offset不包含终点，emoji不拆成半个字符。正文先BOM/换行/首尾空白规范化，所以详情与偏移指向同一份文本。

**本地倒排检索**：对标题和每片正文NFKC规范化/转小写，连续汉字生成相邻二元组，英文数字序列按词处理，忽略部分问话词及英文停用词。中文通常没有空格，不能直接假设空格分词能覆盖查询；MySQL官方[ngram说明](https://dev.mysql.com/doc/refman/8.0/en/fulltext-search-ngram.html)也说明此类分词需求。本实现是Java生成词元并持久写入MySQL倒排表，未使用MySQL原生FULLTEXT，也没有嵌入向量。

词元匹配条数除以查询词元数得到keywordCoverage；1个词元查询须至少1个匹配，多个须至少2个且覆盖率≥0.3。按匹配数降序、chunkId升序稳定排序，最多读200个候选，返回topK≤5。标题词元加入每个片段，因此可能返回同一文档的多个片段；没有去重多样化/语义重排。此分数不表示事实可信度、语义概率或原设计的相似度0.6。

**原子更新与并发保护**：事务内SELECT FOR UPDATE锁定目标，expectedRevision必须等于当前revision。编辑同步替换所有旧分片/词元，完成后indexedRevision=currentRevision；启停只改状态，原文没变，索引代次同事务跟随；删除文档逻辑删除但清掉分片。并发两个写者只有一个能成功。重建旧正文若发生规范化变化，则正文版本也+1，不留下偏移与全文不一致。

读取仅使用index_method=LOCAL_NGRAM且indexed_revision=revision的文档及同代分片。事务读快照保证看到一致数据；本地单篇重建没有额外全局维护开关。有公开资料而全部索引不可用时明确503，避免将准备失败当无匹配；部分文档未就绪时只返回就绪集合，不保证已覆盖所有待索引资料。真正的全局向量索引维护策略留给后续阶段。

**来源隔离**：知识status=1、deleted=0只是第一层条件；有source_id时还检查关联目录公开、未删除，路线同时检查父目的地。检索和详情使用同一来源条件，目录下架后不会留下公开正文旁路。source_id为空的旧资料兼容独立原文，不猜目标。GUIDE新文档不能带关联ID，目的地/路线新文档必须选择真实来源。

**页面安全与错误恢复**：摘录/全文用Vue文本插值及pre展示，TXT/MD不作为HTML执行。页面等待期间阻止重复提交，检索输入变化清旧结果、过期响应丢弃；管理表单409保留输入，重新编辑读服务器新版本。管理员和用户入口都有后端鉴权，前端路由限制只是体验层。上传大小/扩展名/编码/正文范围在服务器复查，客户端约束不作为安全边界。

本地检索不调用模型、不扣AI配额、不伪造llm_call_log。原vector_status不标成1，index_method明确LOCAL_NGRAM；将来向量索引可单独演进，避免把词法索引误认为向量已就绪。

## 答辩常见问题

| 问题 | 可复盘的回答 |
|---|---|
| 为什么不直接让AI回答？ | 用户本批选择先本地检索；先把权限、来源、文档生命周期和失败反馈做成可实测基础，暂不引入真实服务成本。 |
| 这是RAG吗？ | 完成知识管理/分片/检索/来源层；本批只返回原文，不含语义向量召回和生成式回答。 |
| 为什么500/50？ | 沿用业务分片约定，片段可读，重叠保留边缘上下文；字符以Unicode计算，已用emoji与SQL验证。 |
| 怎样防止资料过期仍被检索？ | 内容/状态revision与indexedRevision、分片doc_revision同时核对，公开关联来源也实时查询。 |
| 检索不到会怎样？ | 就绪资料无匹配返回matched=false；所有公开资料未索引则503；不编造回答。 |
| 怎样证明测试真实？ | 129项真实HTTP及MySQL检查、44项Edge操作、并发两个真实PUT；响应体、失败、截图、恢复清理都有独立时间戳证据。 |
| 旧数据怎么升级？ | 只增字段/表的幂等脚本，连续执行两次且原10篇正文哈希一致；schema.sql仅用于新空库。 |
| 为什么旧资料不自动链接目的地？ | 名称不是可靠主键，猜测会制造错误引用；管理员须选真实ID，旧资料先提供全文。 |
| 还存在什么局限？ | 无同义词理解、拼写纠错、BM25/语义排序或聊天上下文，资料不是实时信息；规模/并发压测未进行。 |
