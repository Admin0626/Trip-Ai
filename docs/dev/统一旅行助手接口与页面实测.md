## 真实响应与行为

1. 公网服务没有Key：`POST /ai/planner/test` HTTP200，业务code400，message=请填写模型服务的API Key。SQL确认尚无调用日志，不消耗上游模型调用。
2. 同一临时账号填写自己的DeepSeek地址、deepseek-flash和本机Key（测试用Bearer前缀）：连接测试HTTP200/code200，`data.connected=true`、`data.reply="OK"`。页面展示实际reply。
3. 同一临时账号发送杭州一日游、1天/600元/1人公共测试需求：`POST /ai/planner/generate` HTTP200/code200，`source=USER_MODEL`、`attempts=1`、`draft.answer`为中文建议、`dayList`长度1。模型说明了西湖散步、美食、交通与休息；全文及每日结构见脱敏真实证据。这次成功只证明当前供应商的一次完整链路，未验证实时景点开放、交通或价格准确性。
4. 生成完成SQL查询user_plan数量仍0；单独`POST /plan`确认保存后数量1/status0，`GET /plan/{id}`回显原每日标题。文字answer是本次预览，保存对象是可编辑每日行程，不增加回答历史表。
5. 受控服务核对实际Authorization只有一层Bearer，且无DeepSeek专用参数；浏览器实际SSE收到text/event-stream，并将answer与每日行程展示出来。answer含script标签时显示原文字，没有执行代码。
6. 导航只有“旅行助手”；切换查路线/AI沿用需求，清除Key；原/recommend选路线模式、/ai-planner选AI模式，均保持统一导航高亮。刷新/离开/切账号Key不继承，地址/模型按账号记住；新账号得到公开默认值，不继承前一账号的自定义端口。

|只见每日卡片，模型没有直接回答需求|原协议Draft仅title/dayList。|提示词添加answer；服务校验最多4000字符，页面文本展示。旧模型不返回answer仍允许每日预览并说明缺少独立文字建议。|
