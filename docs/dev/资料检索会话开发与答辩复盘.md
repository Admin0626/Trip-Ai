# 资料检索会话开发与答辩复盘

2026-09-29，codex/knowledge-sessions。用户选择暂不接真实模型，本批把已经完成的本地知识检索接入私人会话，支持保存与回看检索历史。使用页面`/knowledge`进入“资料会话”，或直接`/ai/chat`。原AI规划页`/ai-planner`仍是独立功能。

## 可以演示什么

登录→新建资料会话→输入具体地点/关键词→检索并保存→点击完整资料/有效目录来源→重命名→新建另一个会话→切回历史→加载更早记录→删除。管理员停用或修改知识后，用户刷新历史，旧引用隐藏；重新检索得到当前原文。另一个账号即使知道会话ID，也不能读取或修改。

页面明确显示“检索问题/原文检索结果”。assistant只是兼容既有消息表的角色字段，内容为资料片段及提示，没有模型答案。“那里呢”等指代不会利用上一轮推断；每次独立搜索，不宣称完成最近3轮语义上下文或生成式RAG。

## 一次检索如何保证成对落库

认证确定uid，事务查询会话时必须同时满足id、uid、deleted=0、mode=LOCAL_SEARCH，并对会话行加FOR UPDATE。拿到锁后先查requestId；存在且规范化query/topK的SHA256一致就回放原消息，不再查询/追加一轮。相同UUID但输入不同返回409。

新UUID在200轮限制内复用KnowledgeService.search，得到真实本地结果；写LOCAL_QUERY和LOCAL_RESULT两条消息，再更新计数、revision、时间及默认标题，同一事务提交。检索失败整体回滚，不留一条问题或错误计数。唯一索引(session_id,request_id,role)是数据库最后一道防线；行锁串行处理同会话并发，实际双请求验证一首次一回放。

每次有效追加版本+1；重命名/删除拿锁后比较expectedRevision，过期返回409，防止两个窗口覆盖。创建会话锁本人sys_user行后统计活动数量，防止同时创建突破100个上限。消息id游标避免offset在追加时重复，页面内正序显示，加载更早记录按id去重。

## 为什么历史不能直接返回旧JSON

检索时资料公开，不代表几天后仍公开。旧references_json若原样返回，就算知识详情已经404，历史仍能泄漏撤下的正文。本批只将快照留作内部历史线索，向用户返回前按chunkId/docId检查当前公开状态、索引就绪及分片代次，并生成当前标题/摘录/来源链接。

资料停用/删除、正文编辑重建、关联路线或父目的地下架，引用失效，返回失效数量和重新检索提示。matchedAtSearch只表示当时命中，不表示现在还能展示。assistant.content存通用标签，避免绕过references过滤。未修改资料重开可重新展示同一仍有效分片；编辑后旧分片被替换，不把旧搜索假装成匹配新内容。损坏/缺失快照返回安全提示，不能透传原始JSON。

这是读取时的当前可见性检查，不能撤回用户已经见过或复制的内容；页面需刷新，本批没有实时推送或可见性广播。生产备份、审计与保留政策另行制定。

## 网络失败为什么要保留UUID

“响应没收到”与“服务没成功”是两种状态。后端可能已提交，浏览器不知道；直接新建UUID重发就会多一轮。页面在发送前生成UUID并保存原query/topK，网络失败提示“重试这次检索”，保持原始输入。用户明确“改为新的检索”才能取消待确认请求。

审查时发现刷新会话会清空待确认UUID，已修复为同会话刷新保留它及当前编辑草稿。实际Edge验收先请求真实服务成功，再丢弃响应，刷新并重试得到原消息ID且SQL仍2条。UUID只在当前页面内存，离页/账号切换会清理；本批没有跨设备或浏览器崩溃后的持久恢复能力。

接口回放仍重新验证当前资料可见性；幂等指不重复写入，不承诺原文永远相同。到200轮上限后原成功UUID仍可回放，只有新增轮次被拒。

## 旧表兼容与部署

沿用llm_chat_session/message，不再建一套聊天表。session增加mode/revision，message增加message_type/request_id/request_hash；新增分页和请求角色唯一索引。旧模式/消息默认LEGACY，NULL requestId允许旧消息保留，新接口仅访问LOCAL_SEARCH。29张表总数不变。

升级SQL通过information_schema检测后执行DDL，可重复运行；已有库依次运行知识层和会话升级，不能重建库。MySQL DDL不是业务事务回滚，部署前备份并在测试环境验证。当前原聊天表为空，兼容验证用专属LEGACY夹具，不能据此声称生产大量历史迁移已经验收。

标题最多100 Unicode字符、问题2—200字符、最多5引用；每用户100活动会话，每会话200轮。这些是资源保护的实施限制，不是AI计费规则；本地检索不扣模型quota，不写伪造模型日志，tokensUsed=0。

## 实测和缺陷解释

最终真实接口146/146、Edge55/55；知识129/129、基础21/21、改密认证75/75回归；Maven33/33与前端类型/构建通过。详见[全部响应、失败和方案](资料检索会话接口与页面实测.md)。UUID夹具复用、用户名22字符和未等历史渲染是三个测试错误，完整失败报告保留；刷新丢待确认UUID是代码审查发现并修复的产品风险，两者分别记录。

容量上限采用SQL准备边界，再真实HTTP验证，不是大规模用户压测；Edge响应丢失注入只丢响应，不伪造服务成功。旧主包体积警告、真实模型质量、集群负载未解决。本批没有隐藏失败或把报告生成器当作实测。

## 答辩常见解释

| 可能提问 | 可据实际实现回答 |
|---|---|
| 是否完成AI问答？ | 完成本地知识检索与私人历史基础，模型答案/语义向量尚未接入；选择与用户“暂不接模型”一致 |
| 为什么不用sessionId就查询？ | 必须带认证uid检查归属；ADMIN也不能读别人私人历史，测试覆盖全部读写接口 |
| 为什么既有锁又有唯一索引？ | 锁使一对消息和计数作为一次操作，索引保证同请求同角色最终不会重复写入 |
| 幂等和乐观锁一样吗？ | UUID防止重复检索，expectedRevision防止旧窗口覆盖修改，分别解决重试和编辑冲突 |
| 存了原始引用为什么又查询？ | 当前知识权限/版本可能改变，历史返回必须检查现状，避免下架内容继续泄漏 |
| 对话历史会作为模型上下文吗？ | 本批只回看独立检索，没有模型上下文；后续需要独立设计脱敏、长度和引用校验 |
| 如何证明不是假测试？ | HTTP证据包含请求/响应与SQL检查；Edge实际请求并演示成功后丢响应再回放同消息ID |
| 为什么不直接清库？ | 已有业务要保留，增量SQL只增加字段/索引；夹具仅清所属数据与Redis状态 |
